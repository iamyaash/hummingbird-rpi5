# 8250_bcm7271.ko

[Back to the kernel changes](kernel.md)

## What it's for

The Pi 5's Bluetooth chip is wired to a Broadcom UART (`serial@7d50c000`, compatible
`brcm,bcm7271-uart`). `8250_bcm7271` is the driver for that UART.

## The problem

Fedora doesn't set `CONFIG_SERIAL_8250_BCM7271`. Without it the UART never comes up, so there's
no Bluetooth controller (`hci0`). Everything else in the Bluetooth stack is already in Fedora's
kernel.

## What we ship

[`kmod/bcm7271-uart`](../../kmod/bcm7271-uart/) builds the **unmodified upstream driver** out of
tree. The files are copied from the kernel.org stable tree:

| File | What it is |
|---|---|
| `8250/8250_bcm7271.c` | The driver |
| `8250/8250.h` | Private 8250 header, so it has to match the running kernel |
| `serial_mctrl_gpio.h` | A header the driver includes |
| `VERSION` | The kernel version the files came from (currently `7.3.3`) |

It's installed to `/usr/lib/modules/<kver>/extra/8250_bcm7271.ko`.

## How Bluetooth comes up

```text
device tree alias brcm,bcm7271-uart
  -> 8250_bcm7271 loads, the UART comes up
  -> hci_uart + btbcm load the Pi 5 firmware patch
  -> hci0 appears and bluetoothd takes over
```

Only the first step is ours. The rest is stock Fedora.

## After a base image bump

Because `8250.h` is private, the build fails on purpose if `VERSION` doesn't match the base kernel.
Pull the sources for the new version and commit them:

```sh
make -C kmod/bcm7271-uart update KVERSION=<x.y.z>
```

## Things to know

- It isn't signed, so it taints the kernel. It still loads because Fedora doesn't set
  `MODULE_SIG_FORCE`.
- Every Pi 5 probably ends up with the same Bluetooth address, `43:45:C0:00:1F:AC`. See
  [known issues](../known-issues.md).
